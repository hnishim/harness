# Remote Implementation Loop

## 役割

最初に `../implementation-loop/SKILL.md` とLinearステータスに対応する基準となる参照文書を読み、そのフェーズの意味をそのまま適用します。このリモート環境向け差し替え層が差し替えるのは、ローカル環境の作業ツリーを利用できない場合のGit実行主体と、リモート環境で実行できない受入確認の引き継ぎだけです。レビューの意味づけは基準となる実装ループを維持します。

## 対象判定

リモート環境向け差し替え層は軽量プロファイルを対象とし、課題モードではなく現在のフェーズが要求する機能をフェーズ開始時に判定します。

- `Bug` / `Spike` ラベル自体は対象判定の除外条件にしない。基準となるモード判定を補助するラベルとして対応する参照文書を選ぶ
- 現在のフェーズに必要な機能をLinear、GitHubリポジトリの読み書き、リポジトリ確認、外部サービス、CIなど現在利用可能なリモート側の機能で満たせる場合は共通ワークフローを継続して進める
- 現在のフェーズがリモート環境から利用できない `local-only` または `unavailable` の機能を要求する場合は停止し、その観測・検証・受入確認を `未検証` のまま引き継ぐ。必要な実行入口、実行環境、期待結果、未確認理由をLinearへ残す
- `Strict profile` は対象外。厳格レビュー担当をリモート環境向け差し替え層で代替せず、基準となるローカル `implementation-loop` へ引き継ぐ
- 独立レビュー担当の利用可否は対象判定の条件にしない。レビューを現在のリモート実行から独立に実行できない場合は基準となるレビューステータスで引き継ぐ
- ローカル環境の作業ツリーを利用できずGitHubリポジトリの読み書きが利用可能な場合だけリモート環境のGit実行主体を使う。ローカルGitが利用可能な環境のGit転送は置換しない

リモート環境向け差し替え層固有のステータスやラベルは追加しません。停止時は課題、ステータス、基準となる計画、コメント、ラベル、依存関係とリポジトリの証跡を再取得確認し、停止理由と再開地点を永続的に残します。

## レビューの境界

計画レビュー／テストレビュー／`Test not required` の実装レビュー／Spike結果レビューなど基準となる実装ループが要求するレビューは、成果物作成主体とは独立した読み取り専用レビュー担当で行います。リモート環境向け差し替え層はレビューを省略したり自己判定へ置換したりしません。

独立レビュー担当を現在のリモート実行から利用できない場合は、基準となる参照文書が要求するレビュー資料をLinear／リポジトリに残し、該当レビューステータスで引き継ぎます。別実行は最新のLinear／Harness／リポジトリの証跡を再取得確認して、そのレビューフェーズだけを実行します。

## Git実行主体の切り替え

ローカル環境の作業ツリーを利用できずGitHubリポジトリの読み書きが利用可能な対象課題では、論理的な `checkpoint` / `publish checkpoint` の有効なGit実行主体を [references/remote-git.md](references/remote-git.md) に差し替えます。`git-add-commit-push` の意味づけは変更しません。

ワークフローへ返す論理的な結果はローカル環境の実行主体と同じです。

- 候補SHA／基準SHA
- リモート先／`ref`
- 対象範囲／由来の確認結果
- 公開済み／未公開
- 検証結果またはBLOCKEDの理由

人間による受入確認前は候補ブランチだけを更新し、既定ブランチを更新しません。クローズでは受理済み候補SHAを変えずに対象 `ref` へ公開します。

## 検証 / 引き継ぎの条件

自動検証、CI検証、ローカル環境での受入確認、人間による受入確認の意味は基準となる `test.md` / `implementation.md` に従います。

- CIの根拠を受入確認へ使う場合は候補SHAとCI対象SHAを一致させる
- CI PASSをローカル環境での受入確認または人間による受入確認のPASSへ昇格しない
- クローズ時の公開後CI判定は基準となる `../implementation-loop/references/close.md` を基準文書とし、リモート環境向け差し替え層は提供元／コネクタの通信だけを担当する。必須性、公開契機との結び付け、PASS／停止条件をリモート側へ複製しない
- リモート環境でローカル環境での受入確認を実行できない場合は、通常課題を `Awaiting Acceptance` のまま維持し、候補SHA、実行入口、必要な環境／アプリケーション、期待結果、未確認理由を `implementation-completion` 状態へ残す。ローカル環境での受入確認未実行をPASSへ昇格せず、ローカル環境の基準となる実装ループまたは人間へ引き継ぐ
- 人間による受入確認は `Awaiting Acceptance` で明示的人間確認まで未確認として維持する

Chat／Codex等の実行主体名をワークフロー状態にしません。Linearステータス、基準となる計画、コメント、候補SHAを引き継ぎの条件とします。
