# 計画作成 + 計画レビュー

`Backlog` / `Todo` / `In Plan Review` で読む。共通の取り決めとレビュー作法は `../SKILL.md` に従う。

`Spike` ラベルがある場合は [spike.md](spike.md) の計画作成の差分も読む。

`Bug` ラベルがある場合は [bug.md](bug.md) の症状確認、`investigation` 子課題、原因確定条件、計画への引き継ぎを先に読む。

## プロファイル

- `Backlog` / `Todo` でユーザーがこの依頼内に厳格プロファイルを明示指定した場合は、承認済みとして `Strict profile` ラベルを追加できる
- `In Plan Review` から開始した場合は既存ラベルだけを使う

## `Backlog` / `Todo`: 計画作成

`Backlog` と `Todo` は同じ処理を行います。既存計画があれば基準として保持し、なければ新規作成します。`Bug` ラベルがある場合は、計画の作成・更新前に [bug.md](bug.md) の症状確認、調査子課題、原因確定条件を完了します。

1. `Bug` ラベルがある場合は、親Bugの症状確認、調査子課題の存在・`Spike` ラベル・親子関係、調査結果と結果レビューを再取得し、`ROOT_CAUSE_CONFIRMED` の記録を保存・再取得確認する。未確定・結果不明なら計画を変更せずステータスを維持してBLOCKEDで停止する
2. 既存の説明欄、課題、ステータス、コメント、ラベル、依存関係、リポジトリの事実を照合し、正しい部分を維持して誤り・曖昧さ・不足を修正する
3. 目的、範囲、要件対応、リポジトリの根拠、実施項目、受入条件、検証、未確認事項を必要な範囲で基準となる計画へまとめる。`Test required` の場合はテスト戦略もまとめる。課題の範囲または受入確認に関係する条件だけ、下記の実利用経路・仕様・診断・基準文書との同期を独立に計画へ含める。`Bug` モードでは調査子課題の最新結果、確認済みの原因、原因に直接対応する最小範囲、不具合ケースと隣接正常ケースの回帰テストを明記する
4. 通常課題は専用テスト成果物の要否を決め、テストグループラベルを判定と同じ1つにする。`Test required` の場合は主テスト層、失敗発生境界、不具合ケース／隣接回帰、モック／検証用データ／静的検査の未検証範囲を計画で決める。`Test not required` の場合は、`### テスト判定` の理由に既存validator・静的確認等で十分な根拠を記載し、失敗発生境界等がその判断に重要な場合だけ必要項目を追加する。`Bug` モードの判定は常に `Test required` とし、テストグループラベルもそれに一致させる
5. 基準となる計画、レビュー対象の計画・成果物・差分、課題ID、モード、プロファイル、テスト判定、`blockedBy` のスナップショットを計画レビューのレビュー資料へ渡す。あわせて親エージェントが作成するレビュー文脈候補（`approved_scope`、`review_targets`、`meaningful_diff_at_review`、`comparison_basis`、`unverified`）を渡す。`Bug` モードでは調査子課題、`BUG_INVESTIGATION_RESULT`、その根拠と結果レビューもレビュー対象へ含める。`blockedBy` のスナップショットは今回の計画が依存する現在の `blockedBy` の課題IDを昇順で格納した `relations_snapshot` JSON objectとする。`blocks` / `relatedTo` はこのメタデータに含めない
6. 書き込み直前に説明欄／ステータス／ラベル／計画が依存する `blockedBy` を再取得して基準一致を確認し、説明欄／ラベルを保存・再取得確認してから `In Plan Review` へ更新する

### 説明欄の管理範囲 / 基準となる計画の境界

説明欄の管理範囲はエージェントの管理領域ではなく、必要な場合に人間が明示する保護範囲を基準とします。

```text
HUMAN_AUTHORED_START
...
HUMAN_AUTHORED_END
```

エージェント／AIは自動で `HUMAN_AUTHORED_START/END` を付けない・作成しない。マーカー内の内容は変更・削除せず保持します。マーカーがない説明欄はエージェント管理領域という意味ではなく、既存の意味内容を踏まえて整理可能な通常の説明欄です。

旧 `CODEX_LINEAR_ISSUE_DESCRIPTION_START/END` は旧形式の互換入力としてだけ認識し、新規には作成しません。旧形式のマーカーの内外にある既存テキストと意味内容を失わないよう保持しながら現行構成へ正規化し、CODEXマーカーをエージェント／AIの管理範囲や人間による保護の根拠にしません。`HUMAN_AUTHORED_*` または旧形式のCODEXマーカーが複数、片側欠落、逆順、入れ子等の不正・不整合で境界を一意に決められない場合は説明欄を書き換えずBLOCKEDです。

基準となる計画は説明欄内に次の最上位見出しを**1つずつ**持ち、`## 承認済みPlan` から `## 参考情報` の直前までを一意な最上位範囲の境界とします。計画内部の見出しは `###` 以下です。

```markdown
## 承認済みPlan
...
## 参考情報
...
```

基準となる計画は元の説明欄の背景・目的・要件を不要に全文複製しません。既存内容との重複をしない形で、実装・レビューに必要な追加整理と決定だけを保持します。旧形式のCODEX構成を正規化するときも既存の意味内容は保持します。

通常課題の計画には次を1つだけ持ちます。

```markdown
### テスト判定
- 判定: Test required | Test not required
- 理由: <理由>
```

`Test not required` は専用テストコードを追加せず、既存validatorや静的確認等で受入条件を十分に検証できる場合に使います。

## 条件付きの実利用経路・仕様・診断・基準文書確認

### 実利用経路 / 実行入口

リポジトリ上のソースと実利用経路が1段以上分離する場合だけ、受入確認に必要な範囲で次を記載します。

- ユーザーが実際に起動する実行入口
- 実行入口から変更対象までの関連経路
- リポジトリで編集する成果物／パス
- 実行時が参照する成果物／パスと、両者の同一性・対応を確認する方法

対象はホットキー／ランチャー、ラッパー、symlink、生成済み設定、導入／複製済みスクリプト、プラグイン／拡張などです。リポジトリ内で直接実行する純粋関数・単純CLI・Markdownだけの変更には実行経路確認を追加しません。ソースを直接実行した成功は、分離した実行入口の成功と同義にしません。

### 実際の仕様影響

CLI引数、標準出力／標準エラー、終了状態、実行入口、ホットキー、スクリプトパス、設定形式、入出力形式、イベント、実際の呼び出し元が利用するローカルAPIなどの取り決めを変更する場合だけ、実際の呼び出し元／利用側、取り決めを維持するか、同じ範囲で呼び出し元を更新できるかを記載します。計画外の利用側変更が必要なら互換層を追加せず再計画します。

### 診断根拠の保持

失敗調査または実行時検証で診断の根拠が必要な場合だけ、必要な範囲で終了状態、標準エラー／安全なエラー情報、OS／APIエラー、失敗フェーズ、操作識別子、タイムアウト条件などを記載します。取り決め変更の有無とは独立して判定し、常設ロガーや相関IDなどの基盤は追加しません。

### 基準文書との同期

既存の基準文書が管轄する構成要素の責務、状態遷移、モード／プロファイル、モデル割当、永続的な停止境界、主要な情報源の所有関係などを変更する場合だけ、`agent-development-workflow.md` の同期を実施項目に含めます。課題の進捗、テスト結果、一時的な計測、一回限りの詳細は基準文書へ複製しません。

`Test required` の通常課題の計画には、次のテスト戦略を1つだけ持ちます。`Test not required` の課題にはこのスキーマをN/A埋めのためだけに追加せず、`### テスト判定` の理由で受入条件を十分に検証できる根拠を示します。失敗発生境界等がテスト不要の判断に重要な場合だけ、関係する項目を記載します。

```markdown
### テスト戦略
- 主テスト層: 単体 | 結合 | E2E / 受入 | 静的検査 | 手動確認 | 組み合わせ
- 失敗発生境界: <不具合または受入条件が発生する実境界>
- 不具合ケース: <対象Bugでの再現ケース | 該当なし>
- 隣接回帰: <維持する既存正常ケース | 該当なしと理由>
- モック / テスト用データ / 静的検査の未検証範囲: <内容 | なし>
- 状態待ち: <観測可能な状態変化 | 固定待機と理由 | 該当なし>
```

`Bug` モードでは次を必ず満たします。

```markdown
### 原因調査
- 調査子課題: <原因調査 `investigation` 用のSpike子課題>
- 記録: <最新のBUG_INVESTIGATION_RESULTコメント>
- 原因確定条件: PASS
- 確認済み原因: <原因>
- 根拠: <原因を裏付ける証拠>

### テスト判定
- 判定: Test required
- 理由: <原因を再現し、修正前FAIL・隣接正常ケースの維持・修正後PASSを検証する回帰テスト>
```

### 一回限り

1回限りの移行／後片付け／埋め戻しは安全な手動手順を優先します。恒久スクリプト／フラグ／専用実行入口は、手作業が複雑・反復的で誤操作リスクが高くスクリプト化が明確に有利で、かつユーザーが承認した場合だけ計画へ含め、理由と承認を記録します。

## 計画レビュー状態

計画保存後は課題、説明欄、ステータス、ラベル、計画が依存する `blockedBy`、コメントを再取得し、保存済みの基準となる計画、レビュー対象、モード／プロファイル、`test_decision`、`blockedBy` のスナップショット、レビュー文脈候補をレビューの引き継ぎ情報として固定します。

`state_key: plan-review` の可変フェーズ状態コメントを計画レビュー状態の唯一の現在スナップショットとして使います。状態コメントが存在しない初回だけ新規コメントを作成し、そのコメントIDを保持します。既存の同じ `state_key` コメントがある場合は、レビュー資料、レビュー文脈、`unverified`、現在の計画／レビュー対象を**同じコメントIDへ更新**します。同じ論理状態について別のコメントは追加しない・作成しない。追記だけのスナップショットを増やしません。

レビュー資料を保存した後、独立レビュー担当は同じフェーズ状態コメントを読み、レビュー結果を**同じコメントへ更新**します。レビュー資料とレビュー結果を別コメントへ全文複製しません。`APPROVE` のような指摘事項のない承認レビューは現在の判定と必要メタデータをこの状態へ更新します。`CHANGES_REQUIRED` / 具体的な `BLOCKED` 等の重要なイベントは共通の不変イベントの取り決めに従い別のイベントコメントへ追記し、フェーズ状態は必要ならそのコメントIDを参照します。

独立レビュー担当を現在の実行から利用できる場合は同一の最上位実行内の別の読み取り専用補助エージェントへ渡してよい。利用できない場合は `In Plan Review` のまま永続的に停止し、`plan-review` 状態のレビュー資料から別Chat等の独立実行へ引き継ぎます。再取得値が保存前の意図と一致しない、または対象・差分を確認できない場合はBLOCKEDです。`relatedTo` / `blocks` の変更だけではBLOCKEDにしません。

## `In Plan Review`: 計画レビュー

計画レビューは常に成果物作成主体とは**独立**した読み取り専用レビュー担当が実行します。実行主体の種類をワークフローのメタデータへ保存せず、実行入口にかかわらずレビュー資料、判定の語彙、ステータス遷移、永続的な停止を同じ取り決めで使います。

レビュー開始時は過去のチャットの結論を前提にせず、課題／ステータス／説明欄／基準となる計画／全コメント／ラベル／依存関係、最新Harnessの基準となる参照文書、リポジトリの根拠とレビュー対象差分を最新状態として再取得します。計画作成主体と同一実行環境で承認判定を確定しません。

基準となるローカル実行で利用可能な既定レビュー担当は次です。

- 軽量レビュー担当: `agents/plan-reviewer-lightweight.toml`（Terra/high、読み取り専用）
- 厳格プロファイル: [strict-profile.md](strict-profile.md) を追加適用
- 判定: `APPROVE` / `CHANGES_REQUIRED` / `BLOCKED`

レビュー担当は要求適合、リポジトリ整合、受入条件、テスト戦略、失敗発生境界、検証可能性、未確認事項、レビュー対象の計画・成果物・差分、モード／プロファイル、テスト判定、`blockedBy` のスナップショットと、計画が課題達成に必要な最小範囲であることを確認します。「実利用経路 / 実行入口」「実際の仕様影響」「診断根拠の保持」「基準文書との同期」の4条件を独立に判定し、成立した条件に対応する範囲だけを確認します。存在確認や静的な根拠だけで実行時成功を認定しません。Bugでは調査子課題の結果、原因確定条件、原因と範囲の対応、回帰テストを確認します。`relatedTo` / `blocks` は範囲・受入条件への実質影響がある場合だけ確認対象にします。

実行方法の結び付け／リモート環境向け差し替え層／実行環境の一般化を含む変更では、旧実行方法固有の暗黙前提が基準となる文書全体に残っていないか、新しい実行環境から旧実行環境固有の機能を除いた反例でも成立するか、既存実行環境側の安全条件を弱めていないか、変更ファイルだけでなく間接的な参照文書が整合するかも確認します。

一回限りの処理の恒久スクリプト／フラグ／専用実行入口は、計画に承認済み例外として記録されていない場合 `scope-removal` とします。

明示的な別要件がない限り、対象は単一利用者の個人Mac上で実行するローカルスクリプトまたは小規模な自動化の信頼できるローカル環境です。計画の抽象化、設定機構、フレームワーク、互換層、依存追加、防御的な基盤、将来対応は、現在の課題要件、既存構成、安全性、データ保全、既存互換性の具体的な必要性と照合します。根拠のない対象範囲外の複雑化は `scope-removal` とします。明示的な課題要件や安全性・データ保全・互換性に必要な複雑さは受け入れ、将来の拡張性、一般論、業界の一般的慣行、文体上の好みだけを理由に受入確認を妨げる指摘にしません。

Spikeでは [spike.md](spike.md) の計画レビュー差分も適用します。Bugでは [bug.md](bug.md) の調査記録、原因と対象範囲の対応、回帰テストを確認します。

基準となるレビュー結果の `decision` は `APPROVE` / `CHANGES_REQUIRED` / `BLOCKED` を使います。`APPROVE` では親エージェントから渡された `test_decision`、`relations_snapshot` をそのまま返し、`plan-review` 状態のレビュー結果として更新します。

- `CHANGES_REQUIRED` → 不変イベント保存とフェーズ状態更新後 `Todo` へ戻して停止
- `APPROVE` → フェーズ状態更新後、`Test required` なら `Test Implementation`、`Test not required` なら `Implementation` へ更新して停止し、人間確認を待つ
- 判断不能 → 共通 `BLOCKED`
