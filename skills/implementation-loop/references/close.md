# Close

通常Issueでは現在candidateへのHuman Acceptance PASS、Spikeでは現在result版へのDECISION_READYを確認し、**人間の明示的なClose指示がある場合だけ**開始します。受入前には公開先を更新しません。

## Closeの開始条件と再開

最新のLinear Issue、approval、delivery、Git作業ブランチ・候補SHA、公開先ref、CI、受入確認の記録を取得します。Plan・承認済みテストmanifestの一致、人間による受入確認と候補コミットの版の対応、Test not requiredの場合のImplementation Review承認を確認します。Spikeでは現在resultと承認版が一致することを確認します。

開始条件を満たさず拒否されたClose指示は、その後も流用しません。途中停止後は候補・承認・指示・公開先の実状態を再取得し、以前の停止記録だけを根拠に判断しません。既に公開済みであれば同じ候補を再度公開せず、変更元・承認対象・現在の公開状況を確認できなければ停止します。再開に必要な確認結果を既存のdeliveryに保存します。

## 統合・公開

対象リポジトリ、Issue専用作業ブランチ、公開先を一意に特定します。書込み直前に公開先ブランチの最新コミット・候補コミット・承認済みの差分・並行して行われた変更・ブランチ保護規則・必須チェックを再取得します。公開先を未受入候補に使用しません。

Pull Requestを利用できるならリポジトリの規則に従って通常の差分確認、CI、統合に使います。ローカルGitで安全な直接統合が可能でリポジトリ側が許す場合はそちらも利用できます。Pull Request利用自体を追加の独立レビューや二重承認の理由にしません。ローカルGitを利用できなくても、必要な権限・証跡があればGitHubのPull Requestを統合できます。

統合後のコミットSHAは候補コミットのSHAと一致しなくても構いません。承認済みIssue差分と最終成果物の対応、競合解決と並行変更の動作影響を確認します。統合によって実質的な差分や動作への影響が生じた場合は、影響を受ける検証・レビュー・人間による受入確認を再実施します。SHAの相違だけでPlan／Test Reviewを失効させません。承認済みテストの修正が必要なら既存のTest Implementationへ差し戻します。

他Issueの変更、公開済み履歴、未コミット・未追跡ファイル、別worktreeを保護します。強制更新、無断の履歴書換え・stash・reset等で競合を回避しません。操作対象・権限・変更差分・書込みが成功したかを確認できない場合は、現在のStatusを維持して停止します。

## CI・公開状態

公開前の実行可能な検証と、リポジトリ側の必須チェックを満たします。Pull Requestでは実際の統合結果を検証したSHAを照合します。検証を実行していない場合、実行結果を確認できない場合、検証に失敗した場合はいずれもPASSと扱いません。公開後の公開済みSHAに対する追加CIを実装ループ独自の一律Done条件にはしません。

公開先ブランチのrefと統合結果を再取得し、承認済みIssue差分が公開されたことを確認します。Gitから取得できる現在の公開状態をLinearの可変フラグとして重複管理しません。

## ローカル反映

ローカル環境への反映が必要かどうかはIssueの利用要件・Plan・受入範囲から判断し、作業を始めた環境だけでは決めません。必要なら公開直後に実際に利用するローカル環境へ安全に同期し、必要なファイル配置・設定の適用・再読み込み・起動方法を確認します。同期・適用・使用確認のいずれかが未完了ならDoneには進みません。

同期は既存HIR-277の非破壊手順を再利用します。公開元fetch、公開先refとローカルブランチのSHA・祖先関係・各worktreeのcheckout状態を再取得します。既に同じSHAなら同期済みです。ローカルが公開先の祖先である場合だけ、対象ブランチを現在checkout中で、indexと追跡済みファイルに未コミットの変更がなく、未追跡ファイルも存在しなければ、fast-forwardのみで更新します。対象ブランチがどのworktreeでもcheckoutされていなければ、旧SHA付きupdate-refで非破壊に更新できます。他のworktreeで利用中、未コミットの変更がある、ローカルブランチが公開先より進んでいる／履歴が分岐している、またはfetch・比較・更新・更新後の確認に失敗した場合は、他の作業を変更せず停止します。別領域の成功を実際の利用環境への反映済みとは扱いません。

リモート公開済みで必要なローカル反映が未完了なら、公開済みの変更を再度公開せず `Awaiting Acceptance` へ引き継ぎ、同期・設定適用・利用確認のうち、未完了の作業を具体的にdeliveryへ記録します。反映不要ならローカル待ちを追加せず、同期を次のIssue開始時まで先送りしません。

## Done・作業ブランチ整理

公開・必要な検証・受入確認・ローカル環境への反映が完了したことを確認して初めて`workflow.toml`の`CLOSE_COMPLETE`でDoneへ進みます。統合済みで未公開コミット・他worktreeの使用・残作業がない場合はIssueブランチを任意に削除できます。削除はDoneの必須条件ではありません。

### Issue専用worktreeの整理

CloseがDoneへ進み、公開と必要なローカル反映・適用・利用確認が完了した後、ローカルの対象Issue専用worktreeを既定で整理します。これはClose完了後の独立した後処理であり、worktreeを削除していないことや削除の失敗だけを理由に、Doneへの変更を遅らせたり取り消したりしません。必要なローカル反映が未完了ならClose自体はDoneに進めず、worktreeの削除も開始しません。remote-only実行でローカルworktreeへアクセスできない場合、削除済みとせず、実際に利用する環境で行う整理作業をdeliveryへ記録して引き継ぎます。後処理だけのために既存の公開・Doneを取り消しません。

1. 削除前の確認：現在のGit状態を再取得し、リポジトリ・対象Issue・専用ブランチ・専用worktreeの対応を一意に確認します。パス名だけで対象Issueとの対応を推定しません。`git worktree list --porcelain` で既定worktree、他worktreeのcheckout先・HEAD・ロック状態を確認し、対象内で `git status --porcelain=v1 --ignored --untracked-files=all` を実行して追跡済み・未追跡・無視対象の変更／残存ファイルを調べます。公開結果と承認済み差分、対象ブランチのHEAD、未公開コミット・残作業を照合します。squash等で公開SHAと候補SHAが異なる場合も、祖先関係のみを公開確認の根拠にしません。公開または必要なローカル反映が未完了なら削除しません。未公開コミット・変更・残作業がある場合は削除しないでください。既定worktreeや他Issueのworktreeは削除しないでください。対象ブランチの対応が不明、ロック済み、別の作業／実行中の作業領域なら削除しません。他プロセスが使用していないことを十分に確認できない場合も削除しないでください。
2. 通常削除：前項の条件がすべて成立した場合に限り、対象worktreeの外にある別の作業領域から `git worktree remove <確認済みの対象パス>` を実行します。対象外の作業領域・ファイルには触れません。`--force`、`rm -rf`、無断の`stash`・`reset`・`git worktree prune`は使用しないでください。ブランチは自動削除しないでください。通常削除が失敗した場合、強制削除へ切り替えません。
3. 事後確認：`git worktree list --porcelain` とファイルシステムの現在状態を取得し、確認済みの対象だけが消え、既定・他Issueのworktreeと各ブランチが残ることを確認します。既に削除済みの場合も最新のGit状態から対象の不存在と他領域の安全を再確認し、削除を繰り返しません。対象を特定できない場合、削除できたか確認できない場合、削除が拒否された場合、削除後の確認に失敗した場合、またはremote-onlyでローカル状態を確認できない場合は、削除処理だけ停止し、既存deliveryへ対象・具体的理由・確認済み事実・未確認事項・ローカル再開条件を記録します。再開時は以前の記録だけで削除可否を決めず、最新のGit状態を再取得します。後処理の失敗を理由に既存のDoneを取り消さないでください。公開済みの変更を再公開しないでください。
