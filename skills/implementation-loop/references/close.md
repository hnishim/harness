# Close

通常Issueでは現在candidateへのHuman Acceptance PASS、Spikeでは現在result版へのDECISION_READYを確認し、**人間の明示的なClose指示がある場合だけ**開始します。受入前には公開先を更新しません。

結果記録のみを成果物とし、公開対象のコード差分や候補コミットを持たないSpikeでは、Git公開・CI・ローカル反映をCloseの必須条件にしません。以下の統合・公開、CI・公開状態、ローカル反映の手順は、該当する公開対象の変更が実在する場合に適用します。

## Closeの開始条件と再開

最新のLinear Issue、approval、deliveryを取得し、公開対象の変更がある場合はGit作業ブランチ・候補SHA、公開先ref、CI、受入確認の記録も取得します。通常IssueではPlan・承認済みテストmanifestの一致、人間による受入確認と候補コミットの版の対応、Test not requiredの場合のImplementation Review承認を確認します。Spikeでは現在resultと承認版が一致し、その版へのDECISION_READYが有効であることを確認します。

開始条件を満たさず拒否されたClose指示は、その後も流用しません。途中停止後は候補・承認・指示・公開先の実状態を再取得し、以前の停止記録だけを根拠に判断しません。既に公開済みであれば同じ候補を再度公開せず、変更元・承認対象・現在の公開状況を確認できなければ停止します。再開に必要な確認結果を既存のdeliveryに保存します。

## 統合・公開

対象リポジトリ、Issue専用作業ブランチ、公開先を一意に特定します。書込み直前に公開先ブランチの最新コミット・候補コミット・承認済みの差分・並行して行われた変更・ブランチ保護規則・必須チェックを再取得します。公開先を未受入候補に使用しません。

Pull Requestを利用できるならリポジトリの規則に従って通常の差分確認、CI、統合に使います。ローカルGitによる安全な直接統合をリポジトリ側が許す場合はそちらも利用できます。Pull Request利用自体を追加の独立レビューや二重承認の理由にしません。ローカルGitを利用できなくても、必要な権限・証跡があればGitHubのPull Requestを統合できます。

統合後のコミットSHAは候補コミットのSHAと一致しなくても構いません。承認済みIssue差分と最終成果物の対応、競合解決と並行変更の動作影響を確認します。統合によって実質的な差分や動作への影響が生じた場合は、影響を受ける検証・レビュー・人間による受入確認を再実施します。SHAの相違だけでPlan／Test Reviewを失効させません。承認済みテストの修正が必要なら既存のTest Implementationへ差し戻します。

他Issueの変更、公開済み履歴、未コミット・未追跡ファイル、別worktreeを保護します。強制更新、無断の履歴書換え・stash・reset等で競合を回避しません。操作対象・権限・変更差分・書込みが成功したかを確認できない場合は、現在のStatusを維持して停止します。

## CI・公開状態

公開前の実行可能な検証と、リポジトリ側の必須チェックを満たします。Pull Requestでは実際の統合結果を検証したSHAを照合します。未実行・結果未確認・失敗をPASSと扱いません。公開後の公開済みSHAに対する追加CIを実装ループ独自の一律Done条件にはしません。

公開先ブランチのrefと統合結果を再取得し、承認済みIssue差分が公開されたことを確認します。Gitから取得できる現在の公開状態をLinearの可変フラグとして重複管理しません。

## ローカル反映

ローカル環境への反映が必要かどうかはIssueの利用要件・Plan・受入範囲から判断し、作業を始めた環境だけでは決めません。必要なら公開直後に実際に利用するローカル環境へ安全に同期し、必要なファイル配置・設定の適用・再読み込み・起動方法を確認します。同期・適用・使用確認のいずれかが未完了ならDoneには進みません。

同期は既存HIR-277の非破壊手順を再利用します。公開元fetch、公開先refとローカルブランチのSHA・祖先関係・各worktreeのcheckout状態を再取得します。既に同じSHAなら同期済みです。ローカルが公開先の祖先である場合だけ、対象ブランチを現在checkout中で、indexと追跡済みファイルに未コミットの変更がなく、未追跡ファイルも存在しなければ、fast-forwardのみで更新します。対象ブランチがどのworktreeでもcheckoutされていなければ、旧SHA付きupdate-refで非破壊に更新できます。他のworktreeで利用中、未コミットの変更がある、ローカルブランチが公開先より進んでいる／履歴が分岐している、またはfetch・比較・更新・更新後の確認に失敗した場合は、他の作業を変更せず停止します。別領域の成功を実際の利用環境への反映済みとは扱いません。

リモート公開済みで必要なローカル反映が未完了なら、公開済みの変更を再度公開せず `Awaiting Acceptance` へ引き継ぎ、同期・設定適用・利用確認のうち、未完了の作業を具体的にdeliveryへ記録します。反映不要ならローカル待ちを追加せず、同期を次のIssue開始時まで先送りしません。

ローカル反映のために人間が同期・起動・GUI操作等のトリガーを行う必要がある場合はHumanをnext actorとして停止し、トリガー後にAgentだけで継続できるならAgentへ戻します。ローカル作業であること自体はHuman待ちを意味しません。

## Done・作業ブランチ整理

該当する公開対象の変更がある場合の公開・必要な検証・受入確認・ローカル環境への反映が完了したことを確認して初めて`workflow.toml`の`CLOSE_COMPLETE`でDoneへ進みます。Doneへの遷移と永続状態のreadback後にAssigneeを解除し、terminal stateにnext actorを残しません。結果記録のみを成果物とするSpikeでは、現在resultのhashとレビュー済みhashの一致、その版への有効なDECISION_READY、明示Close指示が揃っていることを確認します。候補履歴だけを理由にIssueブランチを残しません。Issue専用worktreeと作業ブランチはDone後の独立した後処理で確認・整理します。整理未完了や失敗をDoneの遅延・取り消し理由にしません。

### Issue専用worktreeの後処理

CloseがDoneへ進み、公開と必要なローカル反映・適用・利用確認が完了した後、対象Issue専用のworktree、ローカルブランチ、存在するリモートブランチをこの順で整理します。これはClose完了後の独立した後処理です。Doneへの遷移を確認してから始め、整理の保留や失敗だけを理由にDoneを遅らせたり取り消したりしません。必要なローカル反映が未完了ならClose自体はDoneに進めず、整理も開始しません。リモート専用の実行でローカルworktreeへアクセスできない場合は、削除済みとせず、実際に利用する環境で行う整理作業をdeliveryへ記録して引き継ぎます。

1. 削除前：現在のGit状態を再取得し、リポジトリ、対象Issue、候補SHA、公開先、専用ブランチ、専用worktreeの対応を一意に確認します。パス名やブランチ名だけで対象を推定しません。`git worktree list --porcelain` で既定worktree、他worktreeのcheckout先・HEAD・ロック状態を確認し、対象内で `git status --porcelain=v1 --ignored --untracked-files=all` を実行して追跡済み・未追跡・無視対象の変更と残存ファイルを調べます。対象ブランチが共有・保護対象でなく、他worktreeでcheckoutされていないことも確認します。別の作業／実行中の作業領域ではないこと、他プロセスが使用していないことを確認できない場合は削除しません。自分の作業場所を安全に移せる場合だけ移し、他の端末・Agent・プロセスは終了しません。

公開結果と承認済み差分を照合し、対象ブランチ先端が受入済みcandidateと一致し、追加コミット・未統合作業がないことを確認します。Squash等で公開SHAと候補SHAが異なる場合、祖先関係だけを公開確認の根拠にしません。Pull Request経由では、正しい公開先へPRが実際にマージ済みであり、PR headが受入済みcandidateと一致することを確認します。承認済みbaselineからcandidateまでの差分、PR base/headの差分、統合commitと親から確認できる統合差分を突き合わせます。統合commitが公開先履歴に含まれ、対象ブランチ先端に追加commitがないことを確認します。

直接統合ではPRを要求しません。Closeで記録した公開先の統合前後のSHA、統合commitと親から確認できる差分、承認済みbaselineからcandidateまでの差分、公開された最終成果物を照合します。直接squashではcandidateが公開先の祖先でなくても構いません。統合前後の差分と最終成果物の対応を確認し、候補後の追加commitや未反映変更があれば削除しません。差分は追加・削除、内容、mode、rename、binaryを含めて確認します。Hook実行ファイル、実環境で解決された設定参照、リンク先も確認し、削除後のフックや後続処理が対象worktreeに依存する場合は依存を解消するまで保持します。公開または必要なローカル反映が未完了なら削除しません。未公開の追加commit・変更・残作業があれば削除しないでください。既定worktreeや他Issueのworktreeは削除しません。他プロセスが使用していないことを確認できない場合は対象を削除しないでください。

2. worktree削除：前項の条件がすべて成立した場合に限り、対象worktreeの外にある別の作業領域から `git worktree remove <確認済みの対象パス>` を実行します。対象外の作業領域・ファイルには触れません。`--force`、`rm -rf`、無断の `stash`・`reset`・`git worktree prune` は使用しないでください。通常削除が失敗した場合、強制削除へ切り替えず、ローカルブランチとリモートブランチの削除へ進みません。対象worktreeが既に存在しない場合は、登録と実pathの不存在を確認し、削除を繰り返さず次へ進みます。

3. ローカルブランチ削除：worktree削除後、完全なref名と現在の先端SHAを再確認します。refが既に存在しない場合はその事実を記録し、削除を繰り返しません。まず `git branch -d <確認済みIssueブランチ>` を使います。通常削除がsquashの非祖先関係だけを理由に拒否された場合は、PR経由・直接統合に該当する証跡、公開済み差分との一致、追加コミット・未統合作業なしを確認し、対象refの先端、受入済みcandidate、統合対象候補が完全一致する場合に限り、期待SHA付きで次を使います。

   `git update-ref --no-deref -d refs/heads/<確認済みIssueブランチ> <確認済みcandidate SHA>`

完全なref名と期待SHAを指定します。直前にrefが移動していれば削除を拒否させ、そのrefを保持します。git branch -Dや期待値なしのref削除は使いません。通常削除の失敗がsquash以外の理由、期待SHA不一致、権限・ロック・使用中、または結果不明の場合はそこで停止します。

4. リモートブランチ削除：ローカル整理後に、対象リモート、完全なref名、現在のref先端SHA、統合済みで追加commitがないこと、共有・保護対象でないことを再確認します。リモートブランチがすでに存在しないことを認証済みの照会で確認できた場合は削除を繰り返しません。照会の認証・通信に失敗した場合は不存在と扱いません。ローカルで条件付き削除する場合、確認済みcandidate SHAと取得したリモート先端SHAが一致することを確かめ、次の完全一致条件を指定します。

   `git push --force-with-lease=refs/heads/<branch>:<expected-sha> <remote> :refs/heads/<branch>`

この限定操作は、指定SHAのままの対象Issueブランチだけを削除します。公開先ブランチの履歴更新、無条件の強制更新、保護規則の回避には使いません。期待SHAの変更・lease拒否・権限不足・通信失敗・削除結果不明では停止し、新しいSHAへ差し替えて再試行しないでください。条件付き削除の能力がない環境では削除しません。GitHub APIで読み取った後の無条件削除へ置き換えません。条件付き削除ができるローカルGit環境へ引き継ぎます。

5. 事後確認：`git worktree list --porcelain` とファイルシステムの現在状態を再取得し、対象worktreeの登録とpathがともに存在しないことを確認します。完全なref名でローカルブランチの不存在を確認し、認証済みリモート照会で対象リモートブランチの不存在を確認します。公開先、既定worktree、他Issueのworktreeと各ブランチが維持されたことも確認します。対象が既に削除済みの場合は最新のGit状態で不存在を確認して完了扱いとし、再削除しません。

対象を一意に特定できない場合、ロック済み・使用中・未公開変更がある場合、権限がない場合、削除が拒否された場合、削除結果不明の場合、事後確認に失敗した場合、またはリモート専用でローカル状態を確認できない場合は、整理処理だけ停止します。既存deliveryへ対象、確認済みSHA、統合証跡、段階別の削除結果、理由、確認済み事実、未確認事項、ローカル再開条件を記録します。部分完了した操作は繰り返さず、再開時は以前の記録だけで判断せず最新のGit状態を再取得します。削除の保留・失敗を理由にDoneを取り消さないでください。公開済みの変更を再公開しないでください。
