# Strict Profile

厳格プロファイルは、承認済みPlanの範囲・方針・受け入れ基準を変更せずに、テスト設計、実装、独立レビューを行う手順です。

## 開始ゲート

エージェントを起動する前に、次を確認します。

1. 具体的な承認済みPlanを1つ特定し、ユーザーの承認またはそのPlanの実行依頼を確認します。
2. 範囲、受け入れ基準、制約、検証、保持すべき既存変更を記録します。製品、互換性、セキュリティ、失敗処理の方針が未決定なら PLAN_INCOMPLETE として停止します。
3. リスクに応じて small、stateful、high-risk に分類し、受け入れ・リスクマトリクスを作ります。Planから直接導ける最小限の基準は derived baseline と明記し、好みや実装詳細を追加しません。
4. 公開動作単位でシナリオをまとめます。small は原則2〜4個、stateful は4〜7個、high-risk は記載されたリスクに必要な故障注入・手動確認だけとします。通常の新規シナリオは原則7個を上限とし、超える場合は理由を記録します。既存回帰テストと必須手動確認はこの上限外です。
5. 自動化できないランチャー、GUI、権限、ネットワーク、外部システム、ドキュメントの意味は、具体的な手動確認にします。対象外の境界値、形式不正、依存関係、クリーンアップ、シグナル、セキュリティ、プライバシー等は理由付きで N/A と記録します。

マトリクスには次を含めます。

~~~text
change_class: small | stateful | high-risk
automated_scenarios: [public behavior slices]
manual_acceptance: [real checks]
out_of_scope: [category and reason]
scenario_count: N
justification_for_expansion: [only when needed]
~~~

## エージェント契約

- 原則として固定識別子 implementer と reviewer を使います。implementer は medium、reviewer は独立した high 相当の推論設定とし、モデル・設定・サンドボックスはカスタムエージェント定義に従います。
- 利用できない場合は、実装権限を持つ代替implementer、または変更担当でない独立した代替reviewerを、追加承認なしで使えます。代替理由、実効種別、モデル、推論設定（不明なら unknown）を記録し、Plan・範囲・独立レビュー・回数の契約は変えません。
- エージェントは直列に実行し、起動中のimplementer/reviewerを各1つまでにします。可能な限りimplementerを再利用し、テスト専用ゲートのreviewerも再利用します。実装レビューごとに新しいreviewerを使い、終了・中断時は起動した全エージェントを終了します。
- 各エージェントには、承認済みPlan、リポジトリとワークツリーの境界、関連 AGENTS.md、直前の構造化結果だけを渡します。

## フェーズ1：テスト専用ゲート

1. 現在のワークツリーを記録し、既存変更と許可された変更を区別します。implementer にはテスト、fixture、fake、テスト専用ヘルパーだけを許可し、本番コード、実行時設定、ユーザードキュメント、生成物、外部システムは変更させません。
2. 受け入れ基準と該当リスクを、公開動作と外部から観測できる副作用のチェックに変換します。内部設計を固定せず、成功経路、重要な境界・失敗・クリーンアップ・異常終了・セキュリティ・プライバシー・ドキュメント・外部システムを、該当する場合だけ扱います。意味の検証を脆い正規表現やキーワードで代用しません。
3. 既存テストと新規テストを分けて実行し、新規結果を EXPECTED_FAIL、UNEXPECTED_FAIL、PASS に分類します。EXPECTED_FAIL は壊れたテストではなく、欠けた本番動作を示す必要があります。
4. review_phase: tests-only のパケット（Plan、マトリクス、差分、テスト結果、手動確認、既存変更、指示）をreviewerに渡し、網羅性・実行可能性・範囲を独立確認させます。手動確認は、PASS までの対象、担当、アサーション、完了時点を明記します。
5. 判定は TESTS_APPROVED、TESTS_CHANGES_REQUIRED、PLAN_INCOMPLETE のいずれかとします。不正・矛盾・欠落したStatusは同じreviewerに1回だけ言い直させ、それでも不正ならプロトコル違反として停止します。TESTS_CHANGES_REQUIRED は最大2回、2回目なら TEST_DESIGN_BLOCKED として本番変更なしで停止します。PLAN_INCOMPLETE は BLOCKED です。
6. TESTS_APPROVED なら、承認済みテストのファイル一覧、内容ハッシュ、マトリクス、手動チェックを固定ベースラインとして記録します。以後、削除、弱体化、スキップ、変更はできません。無効と判明した場合は実装中に直さず BLOCKED とし、新しいテスト設計ゲートを求めます。

## フェーズ2：実装とレビュー

1. 同じimplementerに承認済みPlan、固定ベースライン、マトリクス、手動確認、リポジトリ境界、テストレビュー結果を渡します。Planだけを実装し、固定テストと追加回帰テストを成功させ、許可された検証を実行させます。
2. レビュー前に、差分とPlan、固定テストのハッシュ、各マトリクス行、必要な故障注入・クリーンアップ・シグナル経路、静的チェック、実動作とドキュメントの一致、未検証事項をimplementer自身に確認させます。BLOCKED、固定テスト変更、重大な逸脱があれば停止します。
3. review_phase: implementation のパケットを作り、新しいreviewerに差分、テスト、故障注入、手動チェック、ドキュメント、範囲を根拠付きで確認させます。評価対象は正確性、Plan適合、範囲、回帰、テスト、セキュリティ・プライバシー・エラー処理、規約です。提案や好みはブロッカーにしません。
4. PASS なら、テスト結果、固定テストのハッシュ、レビュー対象リビジョン、ワークツリー状態が一致することを確認します。CHANGES_REQUIRED なら、3サイクル未満の間だけ、実行可能な指摘ごとに修正前に失敗する回帰テストを追加し、固定ベースラインを保ったまま影響テストと全テストを再実行します。Status不正は同じreviewerに1回だけ言い直させます。
5. CHANGES_REQUIRED が3回目になったら編集を止め、REVIEW_LIMIT_REACHED として不完全な状態を報告します。高重要度の正確性、セキュリティ、プライバシー、データ損失リスクを黙って先送りしません。

## PASS、非PASS、完了報告

PASS は、マトリクス全行が成功した自動・故障注入チェックまたは完了した手動確認で覆われ、固定テストと回帰テスト、静的・実行時チェックが成功し、ドキュメントが実動作と一致し、重要な指摘と高リスクの未解決事項がない場合だけです。

PASS 以外は、全エージェントを終了してから、事実と解釈を分けて次を報告します。承認済みPlanを黙って変更したり、固定テストを弱めたり、同じ終了経路を自動再開したりしません。

- Outcome：停止フェーズ、正確なStatus、レビュー回数、成功・未成功の項目
- Cause：Plan・方針判断、テスト設計、実装、範囲違反、環境、プロトコルのどれかと根拠
- Residual risk：未受け入れ・未検証事項と影響。テストの検出限界と実欠陥を区別
- Options / Recommendation：実行可能な最小限の選択肢、トレードオフ、推奨する次のゲートまたは判断

完了報告には、最終Status、実効エージェント・モデル・推論設定、テストレビュー判定と実装サイクル、固定テストのファイル・ハッシュ、マトリクスと手動確認、変更概要、テスト結果、残る指摘・リスク・未検証事項、無関係な変更を保持した事実を含めます。非PASSなら上記の分析も含めます。
